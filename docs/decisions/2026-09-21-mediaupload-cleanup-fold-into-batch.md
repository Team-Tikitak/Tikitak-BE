# MediaUpload 정리는 completeMedia 즉시 삭제 대신 기존 만료 배치에 편입

- **날짜**: 2026-09-21
- **관련 이슈**: #154 (MediaUpload 레코드 정리 로직 부재)
- **상태**: 결정됨, 적용 완료

## 상황 (Context)
`media_upload` 테이블 row가 어디서도 삭제되지 않아 무한 누적되는 문제. 이슈 자체에 "완료 시점에 즉시 지울지, 기존 만료 배치에 편입시킬지 결정 필요"라고 명시돼 있었다. `MediaUpload`는 `Media`를 1:N으로 소유하고(`media.upload_id` FK, `ON DELETE RESTRICT`), `Media`가 `USED` 상태(피드/데일리질문에 실제 첨부됨)가 되면 기존 배치가 절대 삭제하지 않는다는 게 핵심 제약이었다.

## 검토한 선택지 (Options considered)
1. **`completeUpload()` 완료 시점에 즉시 정리**: 업로드 완료 처리 로직 안에서 자식 `Media`가 모두 처리되면 바로 `MediaUpload`도 지우거나 정리 플래그를 세팅.
2. **기존 `MediaCleanupBatchService` 배치에 4번째 정리 단계로 편입**: "남은 `Media` 자식이 없고 `expiresAt`이 지났다"는 조건만으로 매일 새벽 배치가 하드 삭제.

## 결정 (Decision)
2번(기존 배치 편입)을 선택했다.

## 이유 (Rationale)
- `Media`가 나중에 `USED`가 될 수 있는 시점(완료 직후엔 아직 미사용)과 "업로드 완료" 시점이 다르다. 완료 시점에 즉시 지우려고 하면 이후 `Media`가 실제로 피드에 첨부돼 `USED`가 되는 케이스와 타이밍이 꼬일 위험이 있고, 어차피 FK `RESTRICT`가 막아준다 해도 매 업로드 완료 요청마다 불필요한 정리 체크 로직이 hot path에 붙는다.
- `MediaUpload`는 자체 R2 오브젝트가 없는(오브젝트 키는 `Media.key`에만 존재) 순수 메타데이터 row라서, "자식이 하나도 안 남았을 때"만 안전하게 지우면 되는 문제였다. 이미 존재하는 배치가 정확히 이 타이밍(자식 `Media`가 최종적으로 하드 삭제되는 시점)을 알고 있으므로, 그 뒤에 단계를 하나 이어 붙이는 게 가장 단순했다.

## 트레이드오프 / 남은 리스크
- 배치가 하루 한 번(새벽 4시)만 도니까 즉시 삭제 대비 정리가 며칠 지연된다(아래 orphan-check 결정 파일 참고). 실시간성이 필요 없는 정리 작업이라 문제 없다고 판단.
