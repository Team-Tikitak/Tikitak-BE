# media_upload.expires_at 인덱스는 필터 선택도가 아니라 ORDER BY+LIMIT 최적화 목적으로 추가

- **날짜**: 2026-09-21
- **관련 이슈**: #154 (MediaUpload 레코드 정리 로직 부재)
- **상태**: 결정됨, 적용 완료

## 상황 (Context)
새 정리 배치 쿼리가 `WHERE expiresAt < now ORDER BY expiresAt LIMIT 100` 형태다. 사용자가 "인덱스를 추가할 정도로 효과가 클지"를 되물어서 다시 따져본 판단.

## 검토한 선택지 (Options considered)
1. `V24`에 `media_upload(expires_at)` 단일 컬럼 인덱스 추가.
2. 인덱스 없이 진행(지금 테이블 규모에서 seq scan 비용이 미미할 수 있음).

## 결정 (Decision)
1번(인덱스 추가)을 선택했다.

## 이유 (Rationale)
- `expiresAt`은 `createdAt+7일`로 고정되고 이후 갱신되지 않으므로, 7일 지난 row는 거의 다 `WHERE` 조건을 만족한다 — 즉 **필터 자체의 선택도는 낮아서**, 인덱스가 "매칭 row만 골라내는" 용도로는 효과가 크지 않다.
- 인덱스의 실질 효과는 `ORDER BY expiresAt LIMIT 100`에서 나온다. Postgres가 인덱스를 오름차순으로 걸어가며 100개 채우는 즉시 멈출 수 있어서, 인덱스가 없으면 매일 배치가 "테이블 전체를 스캔+정렬한 뒤 100개만 취함"이 될 수 있고 이 비용은 테이블이 계속 커질수록(이 이슈의 원인 자체) 늘어난다.
- 마이그레이션 자체는 단일 컬럼 인덱스라 무위험에 가까워서, 지금 당장 효과가 작더라도 넣어두는 비용이 낮다.

## 트레이드오프 / 남은 리스크
- 지금 `media_upload` 규모에서 체감 효과는 크지 않을 수 있다 — "당장 필요"가 아니라 "테이블이 계속 커질 걸 대비한 저비용 예방 조치"에 가깝다는 걸 인지하고 넣었다.
- 실 운영 테이블에 인덱스를 거는 자체의 락 문제는 별개 이슈([[flyway-concurrent-index-deadlock]] 참고)로 코드 리뷰에서 지적받아 추가로 처리함.
