### 1-2. 이상 사항: 외부 부하 샘플러의 `docker stats` 누수

`run-measure.sh`가 끝나도 `external-load-sampler.sh`의 `docker stats --format` 프로세스가 남는 문제가 오늘도 재현됐다(스크립트는 범위 밖이라 고치지 않았다).

- 매 측정 뒤 정리를 돌렸지만, 처음 쓴 패턴(`*docker stats --format*`)은 실제 명령줄(`"...\docker.exe" stats --format ...`, 따옴표가 사이에 있음)과 맞지 않았다. 그래서 awk만 종료되고 `docker stats`는 남았다.
- 16:02에 이것을 알아채고 패턴을 고쳐 14개를 종료했다(`raw/growth-leak-cleanup.txt`, `kill(v2)` 줄에 생성 시각이 있다). 생성 시각은 각 측정의 시작 시각과 하나씩 맞는다. 그래서 측정마다 그 전 측정 수만큼 남아 있었다(위 표 오른쪽 열).
- 종료 직전 20초 동안 14개의 CPU 합은 0.086개였다. `com.docker.backend`는 0.058개였다(콘솔 확인, 원시 파일 없음. 그때는 측정이 없었다). Docker VM 안 dockerd의 비용은 재지 못했다(미확인).
- 영향 확인: 누수 0개 상태에서 앱을 다시 띄워 mixed를 한 번 더 쟀다(4-5). P95가 1.0~1.3초 → 0.40~0.56초로 줄었지만 여전히 불합격이었다(dropped 43). 같은 측정에서 앱 재기동과 여유 메모리(1,932MB) 차이도 함께 바뀌어, 누수만의 영향으로 나누지 못했다.

**재측정(3번 기동)에서 한 것.** 기록은 `raw/growth-remeasure-leak.txt`(측정별 `## <RUN_ID>-<mode> pre/post` 단락)와 `raw/growth-remeasure-progress.txt`다.

- 조회 조건: PowerShell `Get-CimInstance Win32_Process`에서 `CommandLine -match 'stats --format'` 또는 `CommandLine -match 'own=tikitak-loadtest-220'`. 따옴표가 섞인 실제 명령줄과도 맞는다.
- 측정마다 `run-measure.sh` 직전(pre)과 끝난 직후(post)에 조회했다. 남은 것은 그 PID만 `Stop-Process`로 끝내고 2초 뒤 다시 조회했다. 다른 docker·awk 프로세스는 건드리지 않았다.
- 결과
  - pre: 앱 기동 전(16:35:05), `20261128-163604`(16:36:06), `20261128-164536`(16:45:37), `20261128-165440`(16:54:41) 모두 0개였다.
  - post: 세 측정 모두 정확히 3개가 남았다. 그 측정의 샘플러가 만든 `awk.exe`(`-v own=...`), `sh.exe`(docker 래퍼), `docker.exe stats --format`이다. 생성 시각 16:36:26~27, 16:45:50, 16:54:55~56은 각 측정의 외부 부하 샘플러 시작과 같다.
  - 3개를 끝낸 뒤 다시 조회해 세 번 모두 0개를 확인했다(16:45:36, 16:54:40, 17:12:53). 앱을 끈 뒤 마지막 조회(17:13:00)와 작업 종료 후 조회(17:13:18, 콘솔 확인)도 0개였다.
- 그래서 판정 회차는 측정 동안 **그 측정의 샘플러 1벌만** 떠 있었다. 이전 측정이 남긴 누수는 없었다.
- **누수는 매 측정마다 재현된다.** `run-measure.sh`가 정상 종료(exit 99, threshold 초과)해도 `docker stats` 스트림이 남는다. 스크립트는 범위 밖이라 고치지 않았다. 측정을 이어 할 때는 측정마다 위 정리를 해야 한다.
- 조회할 때 주의할 점이 있다. 이 패턴을 명령줄 인자로 직접 넘긴 조회(`powershell -Command "... -match 'stats --format' ..."`)는 조회하는 셸 자신(bash·powershell 4개)에 걸린다. 처음 시도(16:29:28)에서 그렇게 4개가 나왔다(콘솔 확인, 원시 파일 없음). 그래서 패턴을 스크립트 파일 안에 두고 `-File`로 실행했다. 그 뒤 조회(16:29:47)는 0개였다. `Stop-Process` 전에 목록의 생성 시각과 명령줄로 자기 자신이 아닌지 확인해야 한다.

- k6는 호스트에서 0.17~0.65개를 썼다. 앱 약 1개, Docker 쪽 2.3~2.8개, 백그라운드 1.7~1.9개와 같은 CPU를 나눠 쓴다.

**같은 호스트 CPU 내역에서 결과가 크게 달랐다.** 재측정 두 mixed(4-2)는 측정 5분 구간의 `-load-host.csv` 분해가 6.42 / 6.41(전체), 2.31 / 2.37(외부), 1.07 / 1.06(앱), 3.04 / 2.98(k6·Docker VM·docker CLI)로 거의 같았다. 그런데 커넥션 점유는 32.8 / 44.8ms, P95는 201~312 / 938~1,171ms였다. 프로세스별 CPU 사용량만으로는 이 차이를 설명할 수 없다(첫 회차의 프로세스별 CPU 파일은 덮어써져 없다, 10절). CPU 클럭(노트북 전력·열 제한), Docker VM 안의 스케줄링, 포트 포워딩 지연은 재지 않았다(미확인).

### 7-3. 성장 시드에서 DB 시간이 가는 곳

DB 시간은 작지만, 어디에 쓰이는지는 #217과 다르다.

- 피드 목록 배치 5종이 mixed DB 시간의 50.8%다(누수 있던 1회차, 상위 1,000개 덤프. 판정 회차는 상위 50개만 남아 계열 합을 내지 못했다, 4절). 그중 댓글 수 배치가 18.9%로 가장 크다(평균 7.92ms, 호출당 read 28.7). `feed_comment` 힙이 661MB다.
- 그다음은 지도 핀 12.3%(썸네일 `feed_image` 읽기)다. 판정 회차도 12.3%로 같다.
- DB 6,565MB가 컨테이너 메모리 2GiB(`shared_buffers` 512MB)보다 커서, 요청당 약 48블록을 디스크에서 읽는다. 무작위로 고른 회원·팀이 98,850명·15,000팀에 퍼져 있어 캐시 적중이 낮다(추정).
- 이 중 어느 것도 기준(P95 300ms)을 넘게 만들지 않았다(solo 전부 합격). #221~#225와 다른 새 이슈 후보로 올릴 근거는 아직 없다. 호스트 한계를 걷어낸 환경에서 다시 볼 대상이다.

## 10. 한계

- **호스트 상태에 민감하다.** 같은 100 RPS에서 P95가 193.5ms(웜업 `20261128-164536-prewarm`)~2.2초(웜업 `20261128-150424-prewarm`)로 달랐다(1-3). 같은 3번 기동에서 연달아 잰 mixed 두 회차도 P95가 3배 넘게 달랐다(4-2).
  - 오염 판정(`LOAD_HOST_AVG_CPU` 2.5)을 넘지 않은 측정도 외부 CPU가 평균 2.15~2.41개였다(각 `-contamination.txt`). 이 PC의 평소 수준(README 10-5, 1.0~1.5)보다 높다.
- **누수 있던 회차는 여유 메모리 2GB 미만에서 했다**(1-1). 판정 회차는 2,164·2,408MB였다.
- **누수 있던 회차는 측정마다 누수 `docker stats`가 0~13개 남아 있었다**(1-2). 호스트 쪽 CPU는 작았지만(14개 합 0.086개), Docker VM 쪽 비용은 미확인이다. 판정 회차는 측정 전후 0개를 확인했다. 다만 누수는 매 측정 뒤 다시 생기므로(`run-measure.sh` 미수정), 측정마다 정리해야 한다.
- **solo는 다시 재지 않았다.** solo는 누수 있던 1번 기동에서 쟀고, 2번째부터는 측정 전 웜업을 하지 않았다(3절). 앞 solo의 캐시 상태를 이어받는다. 요청당 쿼리 수 같은 구조 값은 누수와 관계없지만, solo 지연은 누수 1~7개가 남은 상태의 값이다.
- **EXPLAIN은 부하 직후 상태다.** 1회차도 완전한 콜드가 아니다. 계획 형태와 읽는 행·버퍼를 보는 용도다.
- **Hikari·DB CPU 샘플 간격이 늘었다.** 호스트가 포화된 구간에서 Hikari 샘플은 평균 약 1.8~2초, DB CPU(`docker exec`)는 약 5~5.6초 간격이었다. 표에 샘플 수를 적었다.
- **성능 카운터와 Prometheus의 호스트 CPU가 다르다.** 판정 회차 mixed는 5.99 / 7.98개, 누수 있던 1회차 `-load-host.csv`는 6.56 / 7.93개다. 원인은 확인하지 않았다(미확인).
- **프로세스별 CPU는 표본이 작다.** 10초마다 약 1초 창 하나라, 구간마다 11~28샘플이다. 그 사이의 짧은 변동은 보이지 않는다. 같은 이름 프로세스의 인스턴스 번호가 바뀔 때 비정상 값이 한 번 나왔고 뺐다(7-2-1).
- **재측정 첫 회차(4-1)의 프로세스별 CPU와 측정 전 기록은 없다.** 작업 트리 밖 실행 스크립트에서 출력 경로의 `$rid`가 펼쳐지지 않았다. 스크립트에 쓰려던 `\\$rid`(경로 구분자 + 변수)가 파일을 만들 때 백슬래시 하나가 빠진 `\$rid`로 들어갔다. 그래서 `$`가 이스케이프되고 구분자도 빠졌다. 그래서 세 측정이 모두 `loadtest/results/raw$rid-proc-cpu.csv`·`raw$rid-<mode>-host-pre.txt`에 썼다. 두 번째 측정 샘플러가 시작하며 첫 회차 파일을 덮어썼다.
  - 이것을 16:47에 알아챘다. 실행 중인 스크립트는 고치지 않고, 측정이 끝날 때마다 파일을 `raw/<RUN_ID>-*`로 복사하는 감시 스크립트를 따로 돌렸다(`raw/growth-remeasure-rescue.txt`). 판정 회차 둘은 정상 복사됐다(51·101샘플).
  - 잘못된 이름의 원본 3개는 복사본과 `cmp`로 같음을 확인한 뒤 작업 트리 밖으로 옮겼다.
- **DB CPU 샘플러는 run-measure.sh에 없다.** 작업 트리 밖 샘플러로 16:47:48부터 남겼다. 그래서 재측정 첫 회차(16:40~16:45)는 DB CPU가 없다.
- **판정 회차 mixed의 `pg_stat_statements`는 상위 50개만 있다.** 배치 계열 합은 누수 있던 1회차 값을 썼다(4절).
- **커넥션 점유 중 대기의 정체는 재지 않았다.** CPU 스케줄링 대기, 포트 포워딩, 앱 내부 대기를 나누려면 스레드 덤프·JFR, CPU 클럭 기록이 필요하다(7-4).
- **팀·회원 단위 지연을 나누지 못했다.** k6 CSV에 teamId가 남지 않는다(#217과 같음).
