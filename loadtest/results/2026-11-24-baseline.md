# 조회 API 베이스라인 (#217) — 2026-11-24

피드·알림 대용량 시드 위에서 조회 API 8종(지도 핀, 핀 선택 피드, 피드 첫 페이지, 피드 깊은 페이지, best-attendance, 댓글, 알림 목록, 안 읽은 알림 수)을 측정한 결과다.
계약: `docs/contracts/2026-11-24-read-api-baseline.md`. 절차: `loadtest/README.md`.

원시 파일은 `loadtest/results/raw/`에 있다(커밋하지 않는다). 각 표에 원시 파일 접두사를 적었다. 측정값은 원시 파일에서 그대로 옮겼다. 계산하거나 추정한 값은 그렇게 표시했다.

## 요약

- **mixed(100 RPS 고정 도착률, 5분): 8개 API 모두 불합격.** 모든 API가 P95 약 12~13초이고, 실패율은 0%, `dropped_iterations`는 19,230이다. 실제 처리량은 목표 100 RPS의 약 36%인 35.9 RPS였다.
- **ramp: 25 RPS 단계에서는 P95 209ms(합격선 안)였고, 50 RPS 단계부터 무너졌다.** Hikari pending은 25→50 전환 구간(21:07:27)부터 쌓이기 시작했다. 50 RPS 이상 모든 단계에서 처리량은 35~39 RPS에 머물렀다.
- **원인**: 커넥션 풀(10)이 아니라 Postgres CPU(컨테이너 제한 2개)가 포화됐다. 보조 진단 측정 1분에서 `pg_stat_activity` 샘플이 있는 11샘플 기준으로 Postgres 컨테이너 CPU는 평균 203.8%, 최대 213.9%였다. 같은 11샘플에서 활성 백엔드는 평균 CPU 3.64개, `DataFileRead` 2.36개였다(7-2). 풀 대기는 그 결과로 생긴다(커넥션 획득 평균 2.5초, 커넥션 1회 사용 평균 0.136초).
  CPU를 쓰는 것은 **큰 팀(피드 10만 건) 요청의 쿼리 몇 개**로 추정한다(7-2의 부하 없는 EXPLAIN × 비중 계산). 일반 팀에서는 같은 쿼리가 1ms 안팎이다.
  mixed DB 시간 비중은 지도 핀 38.0%, 안 읽은 알림 수 22.8%, 피드 목록 `count(distinct)` 13.3%다.
- solo(20 RPS, 1분)에서도 불합격한 API는 `map_pins`(P95 6,301ms)와 `feed_deep`(P95 20,866ms)다. 나머지 6개는 solo에서는 합격했다(P95 28~225ms). mixed에서 불합격한 것은 위 쿼리들이 DB CPU를 점유해 생긴 대기 때문으로 추정한다(7-2).

### 큰 팀 요청 비중

k6 스크립트의 비중으로 계산한 기대값이다(실측 아님). k6 CSV의 `url` 칸은 `name` 태그(경로 템플릿)로 바뀌어 요청별 teamId를 알 수 없었다.

- 팀을 고르는 요청(지도 핀 20, 핀 선택 20, 첫 페이지 15, best 5, 알림 목록 10, 안 읽은 수 15, 일반 댓글 10×0.8) × 큰 팀 30%: 0.3 × (0.20+0.20+0.15+0.05+0.10+0.15+0.08) = 0.279
- 깊은 페이지 5%는 모두 큰 팀: 0.05
- 댓글 많은 피드 10×0.2 = 2% 중 큰 팀 306/995(30.8%): 0.0062
- 합계 약 **33.5%** (알림 2종은 큰 팀 멤버의 알림을 조회한다는 뜻이고, 알림 수는 팀 크기와 관계없다)

### 7-2. 풀 대기인가, 쿼리 자체인가

**보조 진단 실행** `raw/20261124-215020-diag-*`(판정에 쓰지 않음): EXPLAIN 뒤 앱을 다시 띄우고, mixed를 짧게(웜업 2분 → k6 웜업 10초 → 100 RPS 1분)돌렸다. 그동안 `docker stats`(Postgres 컨테이너 CPU)와 `pg_stat_activity`(state='active'의 wait event)를 약 3~5초마다 샘플링했다. 결과도 mixed와 같았다: 8개 API 모두 P95 10.8~12.5초, dropped 3,544, pending 최대 190.

| 구간 | Postgres CPU(`docker stats`, 2.00 = 제한) | 활성 백엔드(평균) |
|---|---|---|
| 측정 1분(21:52:48~21:53:50). 두 파일에 모두 샘플이 있는 11샘플(21:52:48은 `pg_stat_activity` 행이 없어 뺐다) | 평균 203.8%, 최대 213.9%, 최소 189.6% (21:52:48까지 넣은 12샘플은 평균 190.0%, 최소 37.9%) | CPU 실행 중 3.64, `IO/DataFileRead` 2.36, `IO/DataFilePrefetch` 0.09 (11샘플 평균) |
| 측정 전 웜업(21:50:25~21:52:24, 24샘플) | 평균 204.4%, 최대 221.0%, 최소 196.8% | CPU 3.42, `DataFileRead` 2.29, `DataFilePrefetch` 0.21 (24샘플 평균) |

판단:

1. **지연의 대부분은 대기다.** mixed 응답 평균은 약 8.4초다. 그러나 요청당 커넥션 점유는 약 0.28초다(3절 Prometheus). 나머지는 Hikari 대기(획득 평균 2.53초 × 요청당 약 2회)와 Tomcat 대기열이다(추정).
2. **풀이 모자란 것이 아니라 Postgres CPU가 포화됐다.** 커넥션 10개가 거의 항상 사용 중인데, Postgres는 CPU 2개를 다 쓰고 있다(측정 1분 11샘플 평균 203.8%). 활성 백엔드 약 6.1개(11샘플 평균 3.64 + 2.36 + 0.09)가 CPU 2개를 나눠 쓰고, 그 중 약 2.36개는 디스크 읽기를 기다린다. 풀을 늘리면 Postgres 안의 대기만 늘어난다(추정).
3. **그래서 쿼리 시간 자체도 부풀었다.** 부하 없는 EXPLAIN과 mixed 평균을 비교한다. 지도 핀은 큰 팀 117.6ms, 일반 팀 1.05ms라 30:70 가중 평균은 약 36ms(계산)인데, mixed 평균은 307.0ms다. 피드 수는 큰 팀 62.5ms인데 solo feed_deep에서 282.1ms였다. 약 4.5~8.5배(계산)이고, 그 차이는 CPU 대기다(추정).
4. **CPU를 쓰는 것은 큰 팀 쿼리다.** 일반 팀은 모든 쿼리가 1ms 안팎이다. 100 RPS mixed 비중에서 부하 없는 실행 시간 × 호출 빈도로 DB 시간 수요를 계산하면 다음과 같다(**추정**: EXPLAIN 2회차 값 × 비중, 큰 팀 30%. 병렬 워커 CPU와 I/O 대기는 뺐다).

| API(RPS) | 계산 | DB 시간 수요(ms/초) |
|---|---|---|
| map_pins (20) | 20 × (0.3 × 117.6 + 0.7 × 1.05) | 720 |
| feed_by_place (20) | 20 × 0.3 × (52.8 + 17.7) + 20 × 0.7 × 약 1 | 437 |
| feed_deep (5, 모두 큰 팀) | 5 × (62.5 + (4.8 + 20.0 + 36.4) / 3) | 415 |
| best_attendance (5) | 5 × (0.3 × 196.9 + 0.7 × 1.08) (병렬 워커 2개 CPU는 별도) | 299 |
| feed_first (15) | 15 × (0.3 × 62.5 + 0.7 × 0.21 + 약 0.5) | 291 |
| unread_count·notifications·comments·배치·단건 | 캐시 상태 기준 | 약 100 이상 (I/O 대기 별도) |
| **합계** | | **약 2,260ms/초 = CPU 약 2.3개** |

   CPU 2개 제한을 넘는다. 25 RPS에서는 약 0.57개라 여유가 있고, 50 RPS에서는 약 1.1개에 병렬 워커와 I/O가 더해진다. ramp에서 25→50 사이에 무너진 것과 맞다(추정).
5. **unread_count는 CPU가 아니라 I/O다.** notification 힙(1,866MB)이 `shared_buffers`(512MB)와 컨테이너 메모리(2GiB)보다 크다. 안 읽은 알림은 힙 블록마다 하나씩 흩어져 있다. 그래서 다른 쿼리가 캐시를 밀어내면 매번 디스크를 읽는다(mixed 호출당 read 234블록, solo 185.9블록). `DataFileRead` 대기 2.36개(11샘플 평균)의 대부분이 이 쿼리일 것이다(추정. 문장별 wait event는 수집하지 않았다).

## 8. 개선 이슈 초안 (생성하지 않음, 사람 승인 뒤 생성)

순서는 mixed DB 시간 비중과 solo 불합격 여부로 정했다. 각 이슈의 검증은 같은 시드(데일리 148,993건 상태) 위에서 개선 전후를 비교한다. 시드를 다시 넣으면 건수 차이를 적는다.

### 이슈 1. 지도 핀 조회가 큰 팀에서 장소 피드 전체를 정렬한다

- **문제**: `FeedRepository.findMapPinsByTeamId`의 `WITH ranked` 쿼리는 팀의 장소 있는 피드를 전부 읽는다. 그다음 `place_id, created_at DESC, id DESC`로 정렬하고 윈도 함수로 장소마다 1행만 남긴다. 피드 수에 비례해 CPU를 쓴다.
- **근거**: 큰 팀 EXPLAIN 117.6ms(60,184행, 힙 19,209블록, 59,897행 버림), 일반 팀 1.05ms. mixed DB 시간의 38.0%(736.7초, 평균 307.0ms). solo 20 RPS에서도 P95 6,301.3ms·dropped 44. ramp r025에서도 P95 320.3ms.
- **개선 후보**: (a) `(team_id, place_id, created_at DESC, id DESC) WHERE deleted_at IS NULL AND place_id IS NOT NULL` 인덱스 + 장소별 최신 1건을 LATERAL/`DISTINCT ON`으로 인덱스 순서대로 읽기. 장소별 피드 수는 같은 인덱스로 index-only count. (b) 팀·장소별 피드 수와 대표 피드를 따로 두는 집계 테이블(쓰기 경로 변경이 필요하다). (c) 짧은 TTL 캐시. (a)부터 EXPLAIN으로 확인한다.
- **검증**: 큰 팀 1·일반 팀 4 EXPLAIN(실행 시간, 읽는 행·버퍼), solo map_pins P95·dropped, mixed의 map_pins P95와 DB 시간 비중. 응답 내용(핀 수, feedCount, 썸네일)이 개선 전과 같은지 비교하는 테스트.

### 이슈 2. 안 읽은 알림 수가 매번 힙을 랜덤으로 읽는다

- **문제**: `NotificationRepositoryCustomImpl.countUnread`는 `count(n1_0.id)`라 `idx_notification_member_unread (member_id, is_read)`만으로 끝나지 않는다. 안 읽은 알림마다 힙 블록을 하나씩 읽는다. notification 힙(1,866MB)이 캐시보다 커서 부하 중에는 디스크 읽기가 된다.
- **근거**: mixed DB 시간의 22.8%(442.5초, 평균 254.6ms, read 406,584블록 = 호출당 234). solo 평균 53.5ms, 호출당 read 185.9. EXPLAIN 회원 983 콜드 156.3ms(read 543, I/O 142.5ms) / 캐시 2.0ms. 이 API의 요청 비중은 15%다(지도 핀·핀 선택 20% 다음).
- **개선 후보**: (a) `count(*)`(또는 QueryDSL `Wildcard.count`) + 부분 인덱스 `(member_id) WHERE is_read = false`로 index-only scan을 유도한다(visibility map이 채워져 있어야 한다. autovacuum 상태도 확인). (b) 회원별 안 읽은 수 카운터(컬럼 또는 Redis). 알림 생성·읽음 처리 경로의 정합성이 필요하다. `teamId` 범위 조회도 있으므로 (a)는 `(member_id, team_id) WHERE is_read = false`도 함께 검토한다.
- **검증**: 콜드·캐시 EXPLAIN(heap fetch 수, read 블록), solo unread_count의 호출당 read, mixed DB 시간 비중. 읽음 처리 뒤 수가 맞는지 회귀 테스트.

### 이슈 3. 피드 목록이 매 요청 전체 수를 `count(distinct)`로 센다

- **문제**: `FeedService.listFeeds`는 첫 페이지든 깊은 페이지든 매번 `countActive`를 부른다. 필터가 없을 때도 `count(distinct f1_0.id)`라 팀 피드 10만 건을 정렬한다. join이 없으면 `distinct`가 필요 없다.
- **근거**: 큰 팀 EXPLAIN 62.5ms(Index Only Scan 100,000행 + Sort 3MB). generic plan은 35.3ms. solo feed_deep에서 평균 282.1ms(요청당 DB 시간의 절반 이상). mixed에서 feed_first·feed_deep 합산 257.5초(13.3%). 목록 쿼리 자체는 첫 페이지 0.72ms다.
- **개선 후보**: (a) place join이 없을 때 `count(f1_0.id)`(distinct 제거). (b) 커서가 있는 요청(두 번째 페이지 이후)에서는 count를 생략한다. `totalCount`의 의미가 바뀌므로 프론트 사용처를 확인해야 한다. (c) 팀별 피드 수 캐시/카운터.
- **검증**: 큰 팀 EXPLAIN, solo feed_first·feed_deep의 count 평균, 응답 `totalCount`가 같은지 비교하는 테스트.

### 이슈 4. 피드 목록 커서 조건이 인덱스 범위 조건이 되지 않는다

- **문제**: `FeedRepositoryCustomImpl.cursor`의 `created_at < ? OR (created_at = ? AND id < ?)`는 OR 때문에 Index Cond가 되지 않고 Filter가 된다. 커서 앞의 행을 모두 읽고 버린다. 깊이에 비례해 느려진다.
- **근거**: 큰 팀 1만·5만·9만 번째 4.8 / 20.0 / 36.4ms, Rows Removed by Filter 10,000 / 50,000 / 90,000, 9만 번째 19,111버퍼. mixed feed_deep 목록 103.3초(5.3%), 평균 158.6ms. solo 평균 212.9ms.
- **개선 후보**: row value 비교 `(created_at, id) < (?, ?)`(QueryDSL `Expressions.booleanTemplate`)로 바꾸면 `idx_feed_active_team_created_id (team_id, created_at DESC, id DESC)`의 범위 조건이 된다. 또는 OR 앞에 `created_at <= ?`를 AND로 더해 범위를 좁힌다. 알림 목록 커서도 같은 형태인지 확인한다. `docs/decisions/2026-11-19-querydsl-feed-list.md`와 연결된다.
- **검증**: 깊이별 EXPLAIN(Index Cond에 created_at 포함, 읽는 행 약 21), solo feed_deep P95. 같은 시각·id 경계 커서 테스트(기존 커서 테스트가 통과하는지).

### 이슈 5. 핀 선택 피드 목록이 인기 장소의 피드를 전부 join한 뒤 정렬한다

- **문제**: `placeId` 필터 목록은 그 장소의 피드를 모두(큰 팀 최다 장소 8,977건) 읽어 team_member·member를 join한 뒤 top-N 정렬한다. 플래너 추정은 16행이다. 추정이 틀리는 이유는 external_place_id를 join으로 거쳐 가서 장소별 쏠림을 모르기 때문으로 보인다(확인하지 않은 해석).
- **근거**: 큰 팀 최다 장소 52.8ms(힙 7,278블록), 장소 count 17.7ms. 일반 팀 0.80ms. mixed 85.4초 + 10.9초(5.0%). 비중 20%(지도 핀과 함께 메인 화면 경로).
- **개선 후보**: (a) `(team_id, place_id, created_at DESC, id DESC) WHERE deleted_at IS NULL` 인덱스(이슈 1 (a)와 같은 인덱스로 둘 다 해결될 수 있다). (b) external_place_id → place.id를 먼저 조회해 `f.place_id = ?` 상수 조건으로 만든다.
- **검증**: 큰 팀 상위 장소·꼬리 장소 EXPLAIN, solo feed_by_place P95, mixed 비중.

### 이슈 6. best-attendance가 큰 팀에서 feed_tag 전체를 병렬 스캔한다

- **문제**: 이번 달 태그 집계가 큰 팀에서 `feed_tag` 전체(약 160만 행) Parallel Seq Scan + Hash Join을 고른다. 한 요청이 프로세스 3개를 쓴다.
- **근거**: 큰 팀 196.9ms(custom plan), generic plan은 Nested Loop인데 콜드 331.5ms. 일반 팀 1.08ms. solo P95 224.5ms, 최대 404.8ms. mixed 51.6초(2.7%)지만 병렬 워커 CPU는 이 수치에 다 잡히지 않는다(추정).
- **개선 후보**: (a) 집계 대상(이번 달 팀 피드)을 먼저 좁히는 형태로 쿼리를 바꾸고, `feed_tag (feed_id) INCLUDE (team_member_id)` 등으로 index-only를 검토한다. (b) 월별·팀별 집계 캐시(이번 달만 갱신). 우선순위는 이슈 1~5 뒤다.
- **검증**: 큰 팀 EXPLAIN(병렬 워커 수, 버퍼), solo best_attendance P95.

### 참고: 이슈로 만들지 않은 것

- **풀 크기·Postgres 리소스**: 포화 원인은 큰 팀 쿼리의 CPU다. 풀 10을 늘리면 Postgres 안의 대기만 늘어난다(추정). 이슈 1~4 이후 다시 재고 판단한다. 운영(Supabase)의 CPU·메모리는 이 환경과 다르다.
- **요청당 커넥션 2회 획득**(토큰 필터 member 조회가 트랜잭션 밖): 커넥션 점유 0.28초 중 단건 조회 몫은 작다(member 평균 0.08~0.21ms). 지금은 영향이 작다(추정).

## 9. 한계

- **로컬 환경**: 앱·DB·k6가 같은 노트북(4코어 8스레드)에 있다. 앱과 DB 사이 네트워크 지연은 거의 없다. Postgres는 CPU 2개·메모리 2GiB로 제한했다. 절대 수치는 dev/prod와 다르다. 같은 환경에서 개선 전후를 비교하는 용도다.
- **soft delete 0건**: `deleted_at IS NULL` 부분 인덱스(`idx_feed_active_team_created_id`, `idx_feed_map_pin_lookup`)와 비부분 인덱스 중 무엇을 고르는지가 실제와 다를 수 있다.
- **데일리 답변 비율**: 목표 20%에 비해 실제 14.9%, 큰 팀 4.1%다(유니크 제약 때문).
- **100 RPS 가정**: 합격 기준 100 RPS는 계약에서 정한 가정이다. 실제 트래픽 근거가 아니다. 이 환경의 상한은 약 36 RPS였다.
- **시드 시각 `LOCALTIMESTAMP`**: 다시 넣으면 데일리 답변 수가 조금 달라진다(이번 148,993건). "이번 달" 피드도 시드 실행 월(2026-11) 기준이라, 달이 바뀌면 best-attendance의 대상 피드 수가 달라진다.
- **큰 팀·일반 팀 지연을 요청 단위로 나누지 못했다**: k6 CSV의 `url`이 `name` 태그로 바뀌어 teamId가 남지 않는다. 큰 팀·일반 팀 차이는 EXPLAIN으로만 봤다.
- **pgss 상위 50개 제한**: IN 목록 길이별로 문장이 갈려 feed_by_place의 요청당 쿼리 수는 추정이다(5절).
- **측정 전 웜업이 매번 포화**: 100 RPS 웜업 2분 자체가 이 환경의 상한(약 36 RPS)을 넘어, 웜업마다 dropped 약 8,300건과 응답 10초 이상이 났다. 웜업 k6가 끝날 때 남은 요청이 연결을 끊어, 앱 로그에 `HttpMessageNotWritableException`(클라이언트 연결 끊김)이 웜업마다 약 100~140건 남았다. 측정 구간에는 들어가지 않았다(래퍼가 남은 요청이 0이 된 뒤 reset한다).
- **보조 진단의 샘플 간격**: `docker stats --no-stream`이 느려 샘플 간격이 1초가 아니라 약 3~5초였다. 측정 1분에 `docker stats` 12샘플, `pg_stat_activity` 11샘플이다.
- **EXPLAIN은 부하 없는 상태**: 부하 중 실행 시간은 CPU 대기로 약 4.5~8.5배 길었다(7-2). 계획 형태와 읽는 행·버퍼를 보는 용도다.
