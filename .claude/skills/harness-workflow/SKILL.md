# 하네스 작업 흐름

너는 **오케스트레이터**다. 직접 코드를 고치지 않고, 워커(`.claude/agents/`)에 일을 나누고, 사람의 승인을 받고, 결과를 코드와 대조한다.
각 단계의 "멈춤"에서는 반드시 사람의 답을 기다린다.

## 0. 시작 점검
- 대상 이슈를 확정한다. 사용자가 번호를 말하지 않았으면 브랜치명, 열린 이슈, 최근 대화로 추정하고, 확신이 없으면 묻는다.
- `gh issue view <번호>`로 본문과 체크리스트를 읽는다.
- `docs/lessons-log.md`에서 이 작업과 관련된 과거 실수를 찾는다.

## 1. 조사 (researcher)
- `researcher`에게 조사를 맡긴다. 프롬프트에 다음을 넣는다.
  - 작업 위치(절대경로)와 이슈 항목
  - 보고할 것: 파일:라인, 모든 사용처(main/test), 기존 패턴, 관련 결정 기록, 런타임 영향(DB·Redis·직렬화)
- 바꾸는 대상이 예외 타입이나 private 메서드라면, **호출부 전체와 경로별 최종 응답 코드를 표로** 내라고 한다. 상위 `catch`가 예외를 다시 던지거나 감싸면 최종 ErrorCode가 바뀌기 때문이다.
- 트랜잭션 경계를 옮기는 작업(`@Transactional` 제거·분리, 별도 빈으로 이동)이면 같은 표에 **트랜잭션 시작 실패와 커밋 실패 경로**를 따로 넣게 한다. 경계가 `try/catch` 안팎으로 옮겨지면 최종 ErrorCode가 바뀌고, 커밋 시점이 외부 호출·Redis 저장 앞뒤로 옮겨지면 부수 효과(푸시 전송, 키 저장 여부)도 바뀐다.
- 롤백 규칙을 바꾸는 작업(`noRollbackFor`/`rollbackFor` 추가, 예외를 던지면서 쓰기를 커밋하게 바꾸기)도 같은 표에 **그 경로의 커밋 실패와 쓰기 중 DB 오류**를 넣게 한다. 전에는 롤백으로 끝나 없던 실패 경로가 새로 생긴다.
- 표의 "이전" 응답도 **호출부별로** 적게 한다. 같은 메서드가 여러 진입점(재발급, 로그인 등)에서 불리면, 같은 실패라도 상위 `catch` 구조에 따라 진입점마다 최종 ErrorCode가 다르다.
- 조사 결과에서 사람이 정해야 할 것(패키지명, 동작 변경 허용 여부, 설계 선택지)을 뽑는다.

## 2. 계약 (멈춤: 사람 승인)
- 결정이 필요한 항목은 선택지와 추천을 함께 제시해 먼저 묻는다.
- `docs/contracts/TEMPLATE.md` 양식으로 `docs/contracts/YYYY-MM-DD-<슬러그>.md`를 쓴다. 꼭 들어갈 것:
  - 항목별 작업과 **범위(건드려도 되는 파일)**
  - **의도된 동작 변경**: 경로별로 이전 응답과 이후 응답을 적는다. 동작 변경이 없으면 "없음"이라고 쓴다. 트랜잭션 경계를 옮기거나 롤백 규칙을 바꾸면 시작·커밋 실패 경로를 빠뜨리지 않는다. 공유 메서드의 동작을 바꾸면 이전·이후 응답을 진입점(호출부)별로 나눠 적는다.
  - 응답 코드, 남은 리스크, 선택지를 기각한 이유도 코드나 실행 결과로 확인한 뒤 적는다. 항목마다 근거(파일:라인, 실행한 명령, DB 동작)를 붙이고, 확인하지 못한 것은 "미확인"으로 표시한다.
  - 완료 조건: 확인 가능한 문장으로 쓴다. 이동 작업이면 rename 판정, 설정이면 기본값의 문자 단위 일치처럼 구체적으로 적는다.
  - 커밋 구성: 한 PR 안에서 커밋을 어떻게 나눌지
  - 하지 말 것
- 승인을 요청한다. 승인받으면 상태를 "승인됨 (날짜)"로 바꾼다.

## 3. 작업 위치
- worktree는 **항상 develop에서 분기한다.** 직접 만든다: `git worktree add -b <브랜치> <경로> origin/develop`
  - `Agent`의 `isolation: worktree`는 원격 기본 브랜치(main)에서 분기하므로 쓰지 않는다.
  - 다른 도구가 만들어 준 worktree라면 `git merge-base --is-ancestor origin/develop HEAD`로 기준을 확인한다.
- 브랜치명은 `<Type>/#<이슈>-<슬러그>` 형식이다. 레포는 `Feat/`, `Fix/`, `Refactor/`, `chore/`를 쓴다.
  - Windows는 ref 대소문자를 구분하지 않는다. 만든 뒤 `git for-each-ref refs/heads`로 실제 이름을 확인한다.
- integrationTest가 필요하면 Docker가 켜져 있는지 미리 확인한다(`docker info`).

## 4. 구현 (implementer, 커밋 단위로 반복)
- **커밋 하나 분량씩** `implementer`에게 맡긴다. 여러 커밋이 같은 파일을 고치면 반드시 순서대로 진행한다.
- 프롬프트에 넣을 것:
  - 계약 경로, 작업 위치, "이번에는 커밋 구성 N번만"
  - 건드리면 안 되는 다음 항목
  - 실행할 명령(`spotlessApply`, `test`, 필요하면 `integrationTest`)
  - "커밋 금지"
- implementer 보고에서 "계약과 다르게 한 것", "이상 사항", "lessons-log 후보"를 챙긴다.
- 환경 문제로 실패했다고 보고하면(예: Docker 미기동) 오케스트레이터가 직접 원인을 확인하고 다시 실행해 본다.

## 5. 검증 (verifier)
- 새 컨텍스트의 `verifier`에게 이번 커밋 범위의 완료 조건을 항목별로 판정하게 한다. 마지막 커밋에서는 계약 전체 완료 조건까지 판정하게 한다.
- verifier의 Bash는 가드 허용 목록으로 제한된다.
  - gradle은 `./gradlew <test|integrationTest|check|spotlessCheck|...>` 형태로만 실행할 수 있다.
  - `$( )`와 따옴표 안의 파이프는 막힌다.
- 테스트가 주장한 것을 실제로 검증하는지도 보게 한다.
  - 같은 에러 코드를 내는 분기가 여럿이면, 의도한 분기에서 끝났는지를 `never()` 검증 등으로 구분하는지 확인한다.
  - 기동 검증과 설정 바인딩은 컨텍스트 단위 테스트로 확인했는지 본다.

## 6. 커밋 (멈춤: 사람 승인)
- 승인 요청은 **한 화면 분량**으로 쓴다.
  - 변경 요약 3~6줄
  - 위험 포인트 2~4줄. 계약에 없던 동작 변경을 찾았으면 반드시 여기에 쓴다.
  - 커밋 메시지
  - "전체 diff가 필요하면 말씀해 주세요"
- 승인받은 뒤에만 커밋한다. 파일은 명시적으로 stage한다. 작업과 관계없는 미커밋 파일은 건드리지 않는다.
- 다음 커밋이 있으면 4단계로 돌아간다.

## 7. critic (Codex)
- 모든 커밋이 끝나면 `bash scripts/codex-critic.sh origin/develop <계약 경로>`를 실행한다. 커밋된 변경만 리뷰한다.
- **지적마다 실제 코드와 대조한다.** critic은 diff 텍스트만 보기 때문에 메서드명이나 사실을 틀릴 수 있다.
  - 지적은 타당 / 사실과 다름 / 부분 타당으로 분류해 사람에게 보고한다.
  - 반영할 것은 후속 커밋으로 넣는다(4~6단계를 다시 거친다).

## 8. PR (멈춤: 사람 승인)
- push와 PR 생성은 사람 승인 후에만 한다. base는 `develop`이다.
- 본문은 `.github/PULL_REQUEST_TEMPLATE.md` 양식을 따르고 다음을 넣는다.
  - 작업 내용
  - **동작 변경 표**(경우 / 이전 / 이후)
  - 검증 결과, critic 반영 내역
  - `closes #<이슈>`
- 하네스 자체를 고치는 변경(lessons-log, 가드, 에이전트 정의)은 기능 PR에 섞지 말고 별도 chore PR로 낸다.
- PR을 만들면 바로 같은 브랜치에서 계약 상태를 "완료 (날짜, PR #)"로 바꿔 커밋하고 같은 PR에 push한다. 다른 PR에서 바꾸지 않는다.
  - PR 승인을 요청할 때 이 상태 변경 커밋과 push도 함께 승인받는다.
  - 머지 전에 문제가 생기면 같은 세션에서 고치고, 필요하면 상태를 다시 바꾼다.

## 9. 마무리
- 이번 작업의 lessons-log 후보를 정리해 사람에게 묻는다.
  - 팀원 누구에게나 해당하는 교훈만 레포에 남긴다. 개인 도구나 개인 환경 문제는 남기지 않는다.
  - 같은 실수가 두 번째로 나오면 린터·테스트·설정·`CLAUDE.md` 규칙으로 승격할지 제안한다.
- 머지가 확인되면 직접 만든 worktree와 로컬 브랜치를 정리한다. `cd`로 worktree 안에 들어가 있으면 지울 수 없으므로 `git -C`와 절대경로를 쓴다.
